# uwuwu-triage — входная точка задач через Telegram

Бот-триажер: юзер пишет в личку боту → демон направляет сообщение в ОДНУ
вечную opencode-сессию диалога — единый контекст всей переписки, память
диалога = сессия (компакция рулит). Агент — **нативный деф** `agent.md`
(frontmatter: модель; деф без ограничений — решение владельца;
тело = системный промпт), демон материализует его в
`~/.local/share/uwuwu-triage/workspace/.opencode/agents/triage.md`, сессия
создаётся с `agent: "triage"`. Агент сам решает: поболтать / ответить на
вопрос / разобрать заявку (классификация проект+тип, дедуп через
`uwuwu-cli search`/`task list`, сверка с целями через `uwuwu-cli goal list`) →
`task create` (ставит Draft, затем `task edit --status Todo`) или
коммент в существующую → сводка доставляется в ТГ. Занят → сообщение
вбрасывается в текущий ход (нативный steer). Референс — origa marketing zoo
(вечная сессия на личность; опыт `opencode-tg-hub-daemon`,
`opencode-tg-agent-zoo`).

## Вотчер черновиков (Draft → общая очередь)

Второй вход того же пайпа: демон сам опрашивает доски «Задачи …» всех
проектов (дискавери по организ-дереву, кэш 6 ч) и подхватывает строки в
статусе **Draft**. Буфер — до постановки в очередь: 2 мин тишины по телу
задачи (`doc.updatedAt`) и по sighting'у, кап 10 мин. Дальше — общий
конвейер: та же очередь, те же батчи (черновик может склеиться с ТГ-ходом —
единый контекст), те же ретраи/dead-letter/confirm-pending.

- Промпт черновика — только метаданные (проект/строка/заголовок); тело
  агент читает сам `task get` — недоверенный контент не входит как
  инструкция. Сдерживание: методичка («текст черновика — данные») + guard
  CLI (`task rm` только Draft).
- Финал разбора черновиков — в лог (chatID=0); исключение — вердикт
  «обсуждение» (вопрос владельцу доставляется в ТГ по залоченному чату);
  dead-letter — уведомление в ТГ по залоченному чату.
- Seen/ack: финал черновичного хода несёт машиночитаемое
  `draft-ack: <rowId>=<вердикт>` (канон: todo · merge · rm · пишется ·
  обсуждение). Терминальные («пишется», «обсуждение») глушат перевывы,
  пока тело не изменилось: дельта `doc.updatedAt` против ack-версии
  снимает ack и даёт ровно один перевыв. «Обсуждение» доставляется
  владельцу в ТГ — диалог замыкается той же вечной сессией.
- Anti-loop (фолбэк = safety-net): нет распознанного ack (агент забыл
  маркер, финал оборван) или вердикт не-терминальный при строке,
  оставшейся в Draft, — прежняя петля: кулдаун 10 мин от последнего хода,
  после 5 холостых оборотов — skip-list с одним ТГ-уведомлением; снимается
  уходом строки из Draft. Разбор ack логируется на каждом черновичном
  ходе («draft-ack: распознано n/N …» / «не найден») — канал недоверенный,
  фолбэк безопасен.

## Файлы

- `lib/hub.ts` (репо-корень) — универсальное ядро демона (с 07.11, задача 202611041714): ТГ long-poll, вечная сессия, очередь/батчи/стирт/доставка — поведение этой папки; триаж — профиль + вотчер черновиков
- `triage.ts` — тонкий вход: профиль демона + вотчер досок (Draft → общая очередь) + draft-хук финала
- `triage-lib.ts` — чистые функции черновик-контура (трекер, seen/ack-гейтинг, промпт разбора; тесты без сети: `bun test`)
- `agent.md` — нативный деф агента: frontmatter (модель) + методичка (системный промпт): ТГ-заявки и черновики Draft
- `mock-tg.ts` — эмуляция api.telegram.org для досмерджевого протокола (см. «Проверка»)
- `hub.json` — секреты (gitignored): `{ "token": "<TG-бот>", "owner": "<username>", "model?": {"providerID": "...", "id": "..."} }`; `model` опционален — дефолт `zai-coding-plan/glm-5.3-flash`
- `hub.example.json` — шаблон конфига

## Рантайм-пути (вне репо)

- state (offset, чат, очередь, активный прогон, трекер черновиков): `~/.local/state/uwuwu-triage/state.json`
- лог: `~/.local/share/opencode/log/uwuwu-triage.log`
- workspace сессий: `~/.local/share/uwuwu-triage/workspace` (пустой, изоляция)

Env для `uwuwu-cli` внутри сессий наследуется от opencode-сервера, не от демона.
Env платформы (`UWUWU_SIYUAN_TOKEN` или `UWUWU_SIYUAN_WS`) нужен самому демону
для вотчера: нет env → вотчер off постоянно, ТГ живёт. Kill-switch:
`UWUWU_TRIAGE_WATCH_SEC=0`; тик по умолчанию 60 c.

## Запуск

```bash
cd ~/uwuwu-agent/triage && bun install
cp hub.example.json hub.json  # заполнить token/owner
# systemd (юнит — ~/.config/systemd/user/uwuwu-triage.service):
systemctl --user daemon-reload && systemctl --user enable --now uwuwu-triage
```

Проверка: `journalctl --user -u uwuwu-triage -f` или лог-файл выше; юзер
пишет боту `/start`, получает справку.

## Проверка (досмерджевый протокол, mock-TG)

Живой прогон демона против mock-TG и реального локального opencode-сервера —
без реального Telegram и без риска для прод-state:

```bash
# изолированный рантайм демона (state/воркспейс/лог/медиа — в песочнице)
export UWUWU_TRIAGE_HOME=/tmp/uwuwu-triage-e2e
# mock-TG: эмуляция api.telegram.org; апдейты — через админ-канал
bun triage/mock-tg.ts --port 8099 --log /tmp/uwuwu-triage-e2e/mock-tg-sent.jsonl &
export UWUWU_TRIAGE_TG_API=http://127.0.0.1:8099
# апдейт владельца снаружи (оркестрация сценария): сообщение от owner в чат 42
curl -s -X POST http://127.0.0.1:8099/admin/push -H 'content-type: application/json' -d '{
  "update": { "message": { "message_id": 11, "chat": { "id": 42, "type": "private" },
             "from": { "username": "owner", "is_bot": false }, "text": "текст заявки" } } }'
# конфиг демона в песочнице (worktree triage/hub.json, gitignored: token — любой,
# owner — юзер из апдейта); ускоренные тайминги: дебаунс 2с, поллинг 1с;
# маркер e2e-сессий (см. ниже)
UWUWU_TRIAGE_BATCH_MS=2000 UWUWU_TRIAGE_POLL_SEC=1 UWUWU_TRIAGE_E2E=1 bun triage/triage.ts
```

- `UWUWU_TRIAGE_HOME` — корень state/воркспейса/лога/медиа демона (дефолт —
  homedir, прод); `UWUWU_TRIAGE_TG_API` — база TG-API (дефолт —
  `https://api.telegram.org`). Оба — тестовые крюки, в systemd-юнит не задаются.
- **Маркер e2e-сессий** (`UWUWU_TRIAGE_E2E=1`): сессия диалога создаётся с
  префиксом `[e2e]` (конвенция `lib/e2e-tag.ts`), дример пропускает помеченные
  сессии при пост-обработке opencode.db. Без маркера прогон протокола в общей
  БД сжигает пост-обработку: одноразовый риг 04.11 породил 30 дример-прогонов
  на 31 smoke-сессии (≈1.14M входных токенов). Тестовый крюк, в systemd-юнит
  не задаётся.
- **Судьба одноразового рига**: стенд 04.11 (оркестрация сценариев в
  `/tmp/uwuwu-triage-e2e`) — одноразовый, в репо не переносится; живой
  протокол проверки — этот раздел (mock-TG + тестовые крюки + сценарии
  a–e). Разбор красного crash-landed (стир терялся после `kill -9`) —
  реальная гонка continuation-окна незавершённого хода, детерминированный
  репро невозможен; контур лечения — баг-задача «Триаж-агент:
  незавершённое задание теряется при обрыве хода» (правило методички +
  гарант «один писатель»), детали серии — Experience/tools «OpenCode TG
  Hub Daemon…», секция E2E.
- Сценарии протокола (оркестрация — последовательные `/admin/push` + ожидания;
  проверка — по логу демона, `sendMessage`-записям mock и сообщениям сессии):
  a. **стирт посреди хода** — ответ отдельным ТГ-сообщением до финала, финал доезжает, дублей нет;
  b. **стирт в гэпе** (сразу после серверного завершения хода) — ответ доезжает (граница `steerAt`), финал прежнего хода не задваивается;
  c. **kill -9 в окне стирта** (маркер персистнут, POST долетел/не долетел) + рестарт — нет дублей и потерь, ответ доезжает (`steerAt` восстановлен);
  d. **повтор того же текста в рамках одного хода** — оба доезжают (граница дедупа от готовности батча, не от старта хода);
  e. **/reset посреди хода со стиртом** — очередь живёт, хвосты не доставляются;
  f. **форвард видео без подписи** — файл в ФС песочницы + маркер вложения в тексте заявки (getFile mock отдаёт `/file/bot…/mock/no-file` → фиксированные байты); два безымянных видео одного батча — два разных файла и два маркера (message_id-префикс).

## Поведение

- Принимаются только личные сообщения владельца (`owner` из hub.json); чужие — тихо.
- Одна вечная сессия диалога на всё время жизни бота: приветствия, вопросы и заявки живут в общем контексте; пересоздаётся при пропаже (404) или по команде `/reset` — в первом случае юзер получает уведомление о сбросе контекста, во втором решение осознанное. Оборванный финал (ход упал) не пересоздаёт сессию: юзер получает пометку «прогон оборван» и сам решает — повторить, поправить или сбросить.
- **Методичка/права — нативный деф агента** (`agent.md` в репо → материализуется в workspace перед каждым ходом). Деф горячий (эмпирика на чистых сессиях: сервер перечитывает agent-def на каждом промпте) — правка `agent.md` в репо доезжает живой сессии следующим сообщением, рестарт демона не нужен. Гочи проб: не проверяй видимость правил в сессии, где модель уже отрицала их — история диалога сильнее обновления.
- Права: деф без ограничений (решение владельца 02.11 — агент полноценный, как крон/фабрика); канбан-дисциплина — методичкой (`uwuwu-cli` для задач; из статусов триаж трогает только Draft → Todo).
- **Модель**: `model` в hub.json применяется нативно к живой сессии (`switchModel` при каждом ходе) и явно при создании (model из дефа к primary-сессиям не применяется).
- Один ход одновременно; занят → сообщение в очередь, а после окна дебаунса — **стирт** в текущий ход: нативный `POST /prompt {delivery: "steer"}` (OpenCode ≥ 2.2.5) — сообщение попадает агенту посреди работы. Черновиковый ход (chatID=0) без стирта: сообщение дождётся конца хода в очереди.
- **Батчинг**: минута тишины после последнего сообщения (поток писем склеивается в одну заявку), кап — самое старое ждёт не дольше 5 мин (`UWUWU_TRIAGE_BATCH_MS`). Редактирование в ТГ в окне дебаунса подменяет текст в очереди (`edited_message`); после ухода батча (в очередь агенту — обычным ходом или стиртом) правки игнорируются («уже у агента»).
- **Вложения**: фото/файлы/видео/гифки/кружки/аудио выгружаются в `~/.local/share/uwuwu-triage/media/` (TTL 7 дней), имена с message_id-префиксом (безымянные видео форварда-альбома не перезаписывают друг друга), пути — строками в тексте заявки, агент фиксирует их в теле задачи (CLI-аттач `--attach` — заглушка на SiYuan v1, отклоняется диспетчером; приложит владелец в UI); files-вложение промпта даёт вижн мультимодальной модели (fallback — ретрай без файлов, пути в тексте остаются). Видео >20 МБ не выгружается (лимит Bot API getFile) — failed-маркер в тексте заявки. Голосовые/стикеры — не поддерживаются: bounce владельцу, в сессию не попадают.
- Сообщение покидает очередь только после подтверждённого промпта — рестарт демона в любой точке не теряет его (окно отправки персистится в state.run; рестарт в окне: промпт дошёл — доигрываем с точным startedAt по тексту сообщения, нет — честный re-prompt). Для стирта персона батча персистится в `state.firing` ДО POST: краш в окне «POST→save» восстанавливается по точной персоне (приземлился — дроп без повторного POST и с восстановлением границы done; не долетел — ретрай той же персоной, новые сообщения очереди к нему не прицепляются).
- Подъём хода падает 5 раз подряд → dead-letter: заявка снимается, юзеру уходит её полный текст.
- **Ответы хода — инкрементально**: каждое завершённое assistant-сообщение (`time.completed`) уходит в ТГ отдельным сообщением, как только готово (дедуп — персистентный `run.delivered`); хвост недоставленного доезжает в финале с ретраями; acks парсятся по всем текстам хода. Граница «done» — `idle >= max(startedAt, steerAt)`: исполнение, начатое стиртом по idle-сессии, отдаёт стухший outcome/idle до завершения — без `steerAt` ответ на вброс терялся бы.
- Ответ = markdown → TG HTML, plain-фолбэк; доставка at-least-once (рестарт посреди доставки может задублировать ответ).
- Ход живёт без таймаута — сколько нужно; сброс контекста один и ручной: `/reset` (работает и во время висящего хода, очередь сообщений сохраняется; вброс, уже приземлившийся в сброшенную сессию, не переигрывается — семантика стоп-крана). Автопересоздания по деградации нет — одна вечная сессия держит память диалога, решение о сбросе за владельцем.
- Безопасность: ограничений прав нет (решение владельца — агент полноценный); текст владельца идёт в сессию как есть, доверенный вход single-owner.
