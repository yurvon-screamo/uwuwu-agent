# Шаблоны тел фабричных задач

Тело задачи — саб-док доски «Задачи <Proj>» (SiYuan database).
Фабрика тело не парсит: агент читает его сам (`uwuwu-cli task get`), спавн-промпт демона —
короткий (см. `factory-lib.ts::spawnPrompt`). Ниже — канон секций, шаблоны и правила формата.
Костяки генерирует `cli/src/siyuan_task.rs::body_template` — этот документ и код сверяет
CI-тест (порядок и состав H2-секций шаблонов).

## Правила формата (обязательные)

- **Markdown должен переживать round-trip SiYuan**: заголовки `##`, списки, жирный.
  Без HTML и вики-синтаксиса `[[ ]]` — они не переносятся через export/import доков.
  Диаграммы — cli-фенсы ```html_embed в `task body` (конвертация реализована:
  именованный фенс = пара «⁂ diagram:<имя> + html», пустой = удаление; skill `visual-diagrams`);
  существующие живые html-блоки тела переживают `task body --replace` (экспорт ядра
  отдаёт их сырым HTML).
- **Без парных тильд вне код-спанов** в markdown-полях тел и комментов: SiYuan парсит
  пару как subscript — два «приближения» в одном абзаце (`~30K`, `~250K`) молча уводят
  промежуток под строку (мутация code=0). Приближения — `≈` или «около», примеры
  с тильдой — только в код-спанах (детали и лечение — опыт
  «platform/SiYuan kernel: блочная модель markdown», секция «Инлайн-парсинг»).
- **Без H1 в контенте тела**: имя дока уже рендерится заголовком, `# {title}` ядро
  импортирует реальным heading-блоком — экспорт получает дубль-H1.
- **Системная секция «Комменты»**: генерируется cli (`task comment`), руками не пишется,
  в вердикты аудита тел не входит; при полной пересборке тела (`--replace`) переносится
  дословно — это история решений (вердикты ревью, ответы владельца).
- **Комменты агентов пишет бот-аккаунт** — демон отличает их от юзерских по автору
  (маркер `🤖` — legacy-фоллбек для старых комментов без автора).

## Канон секций

- **feature** (и все типы фичевого пайпа: docs, other, refactoring, legacy, idea, qa,
  infrastructure): `## Постановка` (контекст → что сделать) → `## План` (в финале агент
  перерастает её в `## Решение` — как устроено и почему) → `## Юзкейсы` (опц.) →
  `## Сиквенсы` (опц.) → `## Проверка` (обяз.) → `## Отчёт инженера` (финальная фаза
  жизни задачи) → `## Смежное` (опц.). Опциональные секции в create-костяк не входят —
  пустые заглушки не плодим.
- **Отчёт инженера** — легальная финальная H2-секция фичевого тела; нутро — H3-подсекции по
  §«Шаблон отчёта» `agents/developer.md` (единственный источник нутра отчёта — этот
  документ его не дублирует).
- **spike**: Контекст → Варианты → Вывод → Границы. Отчёт агента по spike идёт комментом
  🤖 в задачу; follow-up-задачи на найденные проблемы заводит владелец доски.
- **bug**: Сценарий (BDD) → Красный тест → Причина → Фикс → Профилактика. TDD-дисциплина:
  сначала красный тест, не воспроизвёлся — стоп и вопрос владельцу.
- **analys**: проработка/аудит известного без кода — делит костяк spike (Контекст →
  Варианты → Вывод → Границы): метод, находки и выводы в тело, фиксы — отдельными
  задачами. Дисциплина отчёта — как у spike (коммент 🤖, follow-up за владельцем).
- **docs** (доки-работа: синки, гигиена, документация) и **other** (всё прочее) — полный
  пайп как feature, костяк feature (Постановка → План/Решение → Проверка → Отчёт
  инженера). Отдельных канон-секций нет — новые типы обязаны делить костяки
  feature/spike: гард `body_is_skeleton` (task clean) итерирует только
  ["other","spike","bug"]. Тип dev выпилен (20261110180332).
  docs-only финал (правки только в uwuwu-доках) — легален: PR не заводится,
  PR-ячейка = URL главного вики-артефакта (канон финала — AGENTS.md, bullet «docs-only финал»).

## Анти-паттерны (тело — чистовик, не лог)

- Разговорные вставки («я посмотрел…», «ок, поправлю») — безличная форма.
- Логи хода: ход работы — статусы канбана и комменты, не тело.
- Дубли секций; дописывание параграфов вниз без перечитывания целого.
- Живые счётчики («строк 45») — конвенция PR #66: число только с командой
  воспроизведения, иначе качественно.

## Шаблон: feature-задача

```markdown
## Постановка

<контекст → что сделать; ссылки на доки и ADR>

## План

<срезы/шаги, порядок и зависимости; в финале секция перерастает в «Решение»>

## Проверка

<исполняемое: команды, тесты, живой прогон>
```

## Шаблон: spike-задача (исследование)

Для задач, результат которых — вывод и рекомендация, а не фича:

```markdown
## Контекст

<что проверяем и зачем>

## Варианты

<что рассматривали: суть → плюсы/минусы/замеры; сравнение — таблица>

## Вывод

<рекомендация + доказательства: «путь A, потому что …»>

## Границы

<что НЕ исследовано и почему; где вывод не действует>
```

## Шаблон: bug-задача (TDD)

```markdown
## Сценарий (BDD)

Сценарий: <название>
  Дано <состояние мира>
  Когда <действие>
  Тогда <ожидание>  # факт: <что было на самом деле>

## Красный тест

<имя теста, который воспроизводит; не воспроизвёлся на стенде → детали окружения>

## Причина

<механизм: почему система так себя вела>

## Фикс

<что изменилось; красный тест теперь зелёный>

## Профилактика

<как класс бага закрыт: тест/инвариант/линтер>
```
