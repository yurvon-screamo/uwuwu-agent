# AGENTS.md

ALWAYS RESPOND IN RUSSIAN.

> **Platform stack: hub** — private repo `yurvon-screamo/uwuwu-hub` (GitHub): issues = tasks,
> Projects v2 = kanban boards, docs md = wiki.
> Agent transport — uwuwu MCP (uwuwu-server): wiki and boards over GitHub (Contents/Git Data API + Projects v2). Env: `UWUWU_HUB_REPO` (baked into the server), `GH_TOKEN`.

- Provide the user with a working solution only, unless the plan explicitly requires otherwise
- NEVER PERFORM UNSAFE GIT OPERATIONS
- NEVER DELETE CODE YOU DON'T UNDERSTAND!
- NEVER HIDE LINTER ISSUES — FIX THEM OR AT LEAST IGNORE THEM, BUT DON'T HIDE THEM!
- ALWAYS PROACTIVELY USE the `qlty` formatting and linting tool after making code changes — inside a git repository with qlty initialized; otherwise use the project's native toolchain. In the final task report, the Lint/qlty line must follow the delta-vs-baseline spec (canonical spec: agents/developer.md, report template section) — a bare «qlty чисто» is forbidden, it masks the repo's baseline debt.
- NEVER run formatters (prettier, black, rustfmt, …) in the master checkout (`~/uwuwu-agent`) — accidental formatting diffs there are not to be committed or stashed; formatting happens only in task worktrees as part of PRs (`.prettierignore` with `**` blocks prettier repo-wide as a structural guard).
- Any destructive or irreversible operation (file deletion, move/overwrite, force-push, DB migrations) must be preceded by creating a backup. Normal edits are not destructive.

SKILLS rules:

- ALWAYS PROACTIVELY USE SKILLS.
- ALWAYS use SKILLS if there are relevant ones for the task. This is VERY important.
- ALWAYS invoke ALL relevant SKILLS. Don't limit yourself to just one if you see other relevant skills. This is VERY important.

Owner persona (`MCP uwuwu_person_show`) — read it at the start of work on a task: it holds the owner's language, style, and working preferences. If the doc is missing — don't fail, work without it.

Before complicating a solution for a hypothetical race condition or a highly unlikely security scenario, first explain to the user what exactly the problem could be, how likely it is, and what the added complexity costs. Get their consent.
Do not expand the task's scope merely for theoretical robustness.

Statuses for the owner — concise, presented as a table, bullet points, or a list; he doesn’t read long technical reports ("Didn't understand a thing").

## MCP uwuwu — knowledge base

> **Tool contracts come from the uwuwu MCP server's tools/list** (descriptions and argument schemas), not from memory and not from this doc. What is not in the tool list does not exist; a discrepancy — a server task.

- ALWAYS: before a non-trivial task — `MCP uwuwu_search` on the topic. Knowledge accumulation is automatic.
- uwuwu MCP mutations (task_create/edit/claim/comment/close/body, docs_write/append) return the final state or an explicit error. Outside the MCP surface: edits to the goal registry and the persona, semantic maintenance, batch row deletion — open a server task, do not go around it.
- **Transport — hub** (multi-PC: all machines — one GitHub instance). Env: `UWUWU_HUB_REPO` (default `yurvon-screamo/uwuwu-hub`, baked into the server), `GH_TOKEN` (a classic PAT with repo — keyring is locked after reboot and gh hangs). Everything lives in fish universal vars + environment.d.
- An agent takes its own sessionID from the `OPENCODE_SESSION_ID` env — opencode injects it into every shell call of the session (`echo $OPENCODE_SESSION_ID`); it is visible only in the shell tool, opencode terminals do not get it.
- `uwuwu_search` — hybrid: full-text over chunk content + semantics (OpenRouter free embeddings, the index is pulled by the server); section failures are honest strings, not silent blindness. Index maintenance — automatically by a server tick.
- Doc addressing: `uwuwu_docs_read(slug)`, `uwuwu_docs_ls(path)` — the list of a folder's children; `uwuwu_projects` — pipeline projects.
- Notebook branch of `uwuwu_docs_ls(path)`: the prefix-name of an open notebook resolves into the children of its root — `uwuwu_docs_ls(path: "Projects")` lists project folders; a compound «Projects/<проект>» does not resolve (ADR-081).
- `uwuwu_task_*` — kanban tasks (the `project` parameter, default uwuwu): a row = a task (Title/Status/Branch/PR), the body = the issue body, comments = issue comments (threads natively); the title is unique on the board, a raw `/` in a title is valid as is (path_safe sanitizes to ∕ — the carrier was migrated off SiYuan, ADR-017 Superseded by ADR-098). **create idempotency**: a retry after a timeout finds the orphan body by title and re-binds the row, a live row with the same title = a loud duplicate error. `number` — row-id (issue number), resolved within `project`; there is no fuzzy id resolution in MCP. Batch row deletion is not in MCP — board cleanup is the owner's hands (raw-API mutations are their hands too).
- `uwuwu_goal_list(project)` — the project's long-term goal registry: goals = hub-repo milestones (open = in progress, closed = achieved; the project is the `[project]` title prefix). **Rule**: before working on a project task — `uwuwu_goal_list(project: "<proj>")`; goals set the direction — work contradicting an in-progress goal requires an explicit flag to the owner. The goal body is not edited by an agent — the owner maintains it in the UI.


## Task work (uwuwu-hub kanbans)

Take a task to the end — the task body is a living document:
- **the spawn init block is the primary orientation source**: the first factory prompt carries the user/project/task data (the owner persona in full, live project docs via `uwuwu_docs_read`, the task's status cells). No start-up ritual needed: `MCP uwuwu_person_show`, project docs and a repeat `uwuwu_task_get` — as needed (details, fresh status, comments), not as a warm-up. The persona stays compact — it goes into every spawn prompt in full
- **the review pipeline is status-driven, do not call the reviewer**: the plan is settled → plan into the body → `uwuwu_task_edit(number, status: "Plan review")` → end of turn; code + self-check + PR ready → `uwuwu_task_edit(number, status: "Result review")` → end of turn. Reviews are two factory primary agents split by stage: the plan is reviewed by `plan-reviewer` (paraphrase/zoom-out/readiness — methodology `agents/plan-reviewer.md`), the result by `code-quality-reviewer` (methodology `agents/code-quality-reviewer.md`); sessions are independent (each-stage-one-session), the verdict arrives as a wakeup comment on the task: `request_changes` → fix the remarks and back to the review status; plan `approve` → implement; result approve **with minor remarks** (all findings Low) → fix the small stuff and go straight to "Result review" — the same review session runs a delta check, its approve moves the task to "Testing" (a repeat delta round of "Result review" with the same unfixed Lows — the reviewer closes with approve right away, cosmetics do not spin rounds, #1434); a clean result `approve` → also "Testing". **Testing** — a factory primary agent (`tester`, feature quality; methodology `agents/tester.md`): the `pass` verdict — a test-commits checkpoint: with (tester) commits → "Testing review" (reviewed by `test-reviewer`, methodology `agents/test-reviewer.md`), without → `Review` (ball with the user), `fail` (a bug report) → fix it and back to "Result review" — code review of the fix is mandatory before returning to the tester. **Hub**: task comments are issue comments (threads/reply natively), the feed is `uwuwu_task_get` (the comment tail); append semantics — do not duplicate. The review-round cap (all review loops: plan/result/testing): the 4th request_changes in a row without an approve — the pipeline tick itself escalates the row to Needs attention with a digest instead of assigning the next round; after the owner's triage the count restarts
- **the task environment is built by the factory**: on spawn `~/agents-env/<row-id>/{repo, scratch, logs}` are created — repo is a git worktree off origin/master (branch `work/task-<row-id>`), the session starts right in repo; work there, scratch only in `<env>/scratch`, not /tmp. The Branch and Path cells and session binding are written by the factory. Exception — env:false projects (foilcap/true-washing carry real code since #1333; remaining candidate: 1xgames — redmi checkout unverified): create the worktree+branch off origin/master yourself when moving to implementation (after the plan is approved), fill the Branch cell, clean up after the merge. **No «taken» comment** — the kanban status already says it
- **the PR cell is a url type** (rendered as a clickable link), always filled — including docs-only (the URL of the main wiki artifact: a runbook/uwuwu doc; an empty cell reads as «no work»); it holds the main/current PR of the task; a second PR (stacked, remediation) — in the task body or a comment with a native md-link; `uwuwu_task_edit(pr)` accepts only http(s):// (the branch goes into `branch`); create a new project board with the PR column of type URL right away
- **pipeline requests** (no direct orders anymore, #1135): `uwuwu_task_create` sets **Analys** — an analyst will elaborate the request in a wave; no agent self-assigns (do not claim + set your own In Progress) — work is started by the owner via fast-track (moving the row to In Progress) or the pipeline (analyst → Todo → owner → Design)
- **Direct tasks** (a boolean row property, #1357): a direct owner order «here and now» — `uwuwu_task_create(direct: true)` births the row straight into In Progress bypassing the factory stages (Analys/Design/both reviews/testing); the current session does the work, when done it sets `Review` itself (the edge is open only to direct rows), the PR into the cell, ball to the owner. The flag — only on a direct order, the verbatim quote of the order — in the body; Automerge on — only on an explicit owner mandate in the order. The environment of a code direct order — by the agent's hands following the env:false pattern: worktree+branch off origin/master, the Branch cell via `task_edit`, cleanup after the merge (the factory builds no env — there is no spawn). The boundary with /fast: /fast — chat without a kanban row; direct — a full board row bypassing the factory stages
- **the task body is a clean document, not a log**: edit via `uwuwu_task_body` (full replacement: body = clean markdown without fm — the server silently strips incoming fm, ADR-105; the hub overwrites the issue body in place — the issue number is stable); re-read everything, restructure, remove junk and repeats; NEVER append paragraphs at the bottom; tidy formatting is part of the work. The canon of sections and body anti-patterns — [agents/TASK-TEMPLATE.md](agents/TASK-TEMPLATE.md): dev = «Итог» (the first section; appears at the finish, updated by the developer) → Постановка → План (in the final — «Решение») → Юзкейсы (opt.) → Сиквенсы (opt.) → Проверка → «Отчёт инженера» (H3 inner sections — per the agents/developer.md template) → Смежное (opt.); no H1 in the content; comments are real issue comments (not a body section): body-replace does not touch them; your comment — a separate `uwuwu_task_comment`
- **no counters in docs**: do not write counter numbers («45 lines», «12 tasks») — a bare digit rots within a day; if scale is needed — qualitatively («on the order of a hundred lines»), the exact number is taken on the spot by whoever needs it
- type — the «Тип» board column (visible in `uwuwu_task_get`/`uwuwu_task_list`, written by `uwuwu_task_create(type)`/`uwuwu_task_edit(type)`; canon: bug | spike | docs | other | feature | refactoring | legacy | qa | infrastructure — dev was removed 10.11, idea/analys were removed #1135: the owner's ideas are elaborated by the analyst to feature level; the create default without `type` — feature; no more #dev/#bug/#spike tags in bodies): Bug → strictly TDD (first reproduce with a red test; if it did not reproduce — stop and ask the user); Spike → no code writing, the report goes into the body → Needs attention; Refactoring → structural refactoring without behavior change; Legacy → sunset/migration of legacy; Qa → the test contour of the task; Infrastructure → infra work; Docs and Other → the full pipeline as a feature
- diagrams — mermaid in the issue body (GitHub renders it natively) or a picture asset; in wiki docs (docs/*.md uwuwu-hub) — HTML/SVG is rendered as a file; Vesper style, the `visual-diagrams` skill
- reports/questions to the user — `uwuwu_task_comment(number, text)` (an issue comment; the user replies in a comment/thread — a thread wakes the agent); **the user does not read your session** — all communication only in uwuwu
- waiting for the user's answer/decision (a question, an approval) → `uwuwu_task_edit(number, status: "Needs attention")`; the user answered in a comment → **immediately clear Needs attention** and continue: they answered during your turn — handle it in the turn, no status needed
- **Empty status** — the user's legacy draft: the factory does not touch it. New tasks are created straight into **Analys** («tasks are not created into the void»: create sets Analys, the analyst sidecar elaborates batches in waves — sourcing (ADR-102), dedup, editing; the analytics reviewer's verdict → **Todo**; Draft — only the owner's drafts). Todo → **Design** is set by the owner → the factory spawns an agent: the settling stage (study, clarify, plan; questions → Needs attention)

- **Design stage: scan the territory before the plan** — before writing the plan check that the scope territory is free: `MCP uwuwu_task_list` of the project board (adjacent tasks — statuses, scope overlap) + `gh pr list --state all` / `gh pr view` of the repo (open and freshly merged PRs — batch summaries/hygiene quietly eat plan slices, without a trace on the board). The plan references the scan (what adjacent work was found or not); a duplicate found — not a quiet replan but a question to the owner (close as a duplicate vs an independent PR of the remainder → Needs attention). The scan refreshes at implementation time — adjacent tasks and PRs are born in parallel
- **Board pointers — only live**: a string pointer from the statement (another task's row-id/title) enters the plan/body only after a live check `uwuwu_task_get(number)` in the same session — git/env facts are verified against the source, the board is not taken on faith. A dead id — re-resolve a live one by title (`uwuwu_task_list`/`uwuwu_search`) or flag the owner; in text the pointer lives as a pair «row-id + title string», but re-resolution by title is a fallback, not a guarantee (titles change too: UI renames, triage editing) — the final resolution is always confirmed by a fresh `uwuwu_task_get`. Pointers are verified at the moment of use (plan building, review, implementation): a pointer alive at review time and dead by implementation is not a plan defect, but a re-resolution along the way
- **Summary tasks (batch merging of tails)**: a summary item = a live pointer (row-id + title string) + status + the closing PR at assembly time; a table «item → status → evidence» in the body, the evidence — the output of a live check (`uwuwu_task_get`/`uwuwu_task_list`/`gh pr view`), the reviewer re-checks it cheaply and trusts it. Absorbed rows are retired at the summary's finalization (all items merged into the PR, before "Result review"): the summary's agent walks the item table — a live check of each source row; Draft — flag the owner for deletion (no batch deletion in MCP), live — a comment-flag to the owner; the outcome is fixed in the summary table — duplicates do not live in parallel with the summary past finalization
- **Cold box (#1293)**: closed rows older than a week go to the Projects v2 archive and disappear from `task_list`; cold reading — `task_get` by number (works) or `gh search issues --repo yurvon-screamo/uwuwu-hub in:title "…"` by title; `task_close` on a cold row honestly answers «the row is not on the configured boards» — not a breakdown; unarchive — the owner only, in the UI
- **Fast-track**: the owner can move a task to `In Progress` from any status (Todo, Design, …) — this signals the factory to spawn an implement agent **without Design and "Plan review"** (overdrive: small stuff, hotfix class; a short plan — at the agent's discretion, as the body's first section). "Result review" is mandatory as usual. A new (without a factory state record) row in In Progress gets a fresh implement agent; exception — a row with a live dev cell (a `uwuwu_task_claim` request): external work is already running, no spawn; for a factory-**tracked** task a move to In Progress from another status wakes/restarts its agent — «intervene and fix» (a hung round; a PR conflicting with master → conflict-kickoff «resolve, push, back to Result review»). Setting In Progress again on an already-In Progress row does not wake it — the signal is only the status change
- **who sets statuses**: `In Progress` after "Plan review" is set by the reviewer per the verdict; after "Result review" the reviewer sets `In Progress` on `request_changes` and on approve with minor remarks (a delta round), "Testing" — on approve (clean or delta); the tester sets "Testing review" on pass with (tester) commits, `Review` on pass without them and `In Progress` on `fail` (a bug report); the test reviewer sets `Review` on clean and "Testing" on findings; the owner also sets `In Progress` — fast-track (a direct move = an implement-agent spawn, see above); **Design is set by the owner or the reviewer** (`request_changes` on the plan) — the developer does not set it and does not return to it; **Draft** — the owner (a draft), **Analys** — create or the owner (from Draft), **Review Analys** — the analyst, **Todo** — the analytics reviewer (approve), **Wait** — the owner (parking tasks «for later»), **Done** — the owner (merge/acceptance); the automerge daemon merges but does not close (see «Done is set by the owner»). Review statuses are set by the developer as the «ball with the stage agent» signal; "Testing" — the developer from In Progress (branch/PR alive, self-check passed) or the reviewer on a "Result review" approve. **CUP queue**: active (LLM-spending) tasks are capped by `policy.cup` in server/config.toml (default 7, global across projects); new Design/In Progress rows are taken by the factory from the priority queue (high → medium → low; create without `priority` writes priority: medium — the owner's default 13.11, high/low are set explicitly by the owner and the analyst), empty — below low. **Triage fields**: the analyst at triage fills Priority and Automerge explicitly (medium — a decision, not silence; Automerge on/off), an empty required field on a row leaving Analys = a wave defect — the server gates `task_edit` transitions out of Analys with a rejection listing the fields. A Design row may wait for a free slot — that is the queue's norm, not a stall. In the GLM peak window (weekdays 06:00–10:00 UTC = 15:00–19:00 JST, `policy.peak` in server/config.toml, off — `enabled = false`) spawns/wake-ups of non-high tasks are deferred to the end of the window — high tasks keep working. Agents NEVER move their tasks to Todo themselves — the incoming flow is driven by the analyst, the Todo verdict belongs to the analytics reviewer
- PR: `gh pr create` → the URL into the PR cell and a comment on the task (renders natively) → before `uwuwu_task_edit(number, status: "Result review")` honestly wait for green CI in the foreground: `gh pr checks <URL> --watch` (moving a task to review with unrun/red CI is forbidden; repos without PR CI — per the repo doc — CI-watch is skipped: full local verification, the fact goes into the body); after approve (clean or delta-approve after approve-with-notes) the reviewer will set `Testing`; after the tester's `pass` — "Testing review" ((tester) commits present) or `Review`
- **docs-only finish** (edits only in uwuwu docs: runbooks, Deployment, ADRs — repos untouched) — a valid outcome without a PR: CI and merge do not apply; the finish = the engineer report in the body + the URL of the main wiki artifact into the PR cell → `uwuwu_task_edit(number, status: "Result review")` (CI-watch not needed); closing — acceptance of the docs by the owner without a merge. Uploading a doc as a file into a repo — only when the artifact is needed outside the uwuwu contour: it is a deliberate second carrier diverging from the wiki — sync it on every change (the «carry the value, not a copy» principle, the «Docs-drift sweep» experience)
- **a task is not closed until the PR is merged and CI is green** (no PR CI — per the repo doc: the criterion does not apply; docs-only — closing without a merge, see above; GitHub Actions ci.yml: fmt/clippy/test + qlty delta; the reviewer relies on CI statuses — manual runs are not needed) — finish it (watch/fix/push fixes, choose the method yourself); done: the final report — into the body, into the PR — a short digest, a comment «PR ready for merge» → wait for Review
- **Done is set by the owner** (merge/acceptance) — an agent never closes a task itself; exceptions — the automerge daemon (the `automerge` field, default `uwuwu_task_create`: merges the PR on entering Review, **the row stays in Review** — Done always belongs to the owner; the legacy `autodone` field is read; red CI/conflict/no PR — bounce to In Progress with a comment; docs-only with an artifact URL of non-PR form in the PR cell is not bounced by the daemon — it waits for the owner, #1286) and a cron run (not a task, ADR-103 — see «Agent crons»)


- **a review or testing hang** (the status silent in «Review …» or «Testing») → a comment on the task: the factory will wake/restart the session holder

### Testing rounds

After the code review approve (clean or delta-approve) the reviewer sets «Testing» — the factory
spawns/wakes the tester (a primary agent `tester`, 1 task = 1 session, cwd = the task worktree).
The verdict arrives as a wakeup comment on the task: `pass` — a test-commits checkpoint: with (tester)
commits on the branch → "Testing review" (its own contour — below), without → `Review`, ball with the user
(merge/acceptance); `fail` (a bug report with reproduction steps) → the developer fixes the bug,
runs the self-check, pushes and sets "Result review" — code review of the fix is mandatory before
returning to the tester, the re-entry goes into the same test session with a delta prompt (checking
the fix, not a from-scratch re-review). The tester additionally covers the code with tests (commits to
the task branch, push before the verdict) — production code untouched. A third `fail` round in a row on the same
bug → deadlock to the user (a comment, `Needs attention`), no fourth round.

**Testing review**: pass with (tester) commits moves the row to the
test-reviewer (`agents/test-reviewer.md` — the test delta after the code review approve
was reviewed by nobody): clean → `Review`; High/Common → "Testing" (the tester fixes
their tests); all Low → approve-with-notes → fix → a delta round of the same role. The round
cap is shared with the review loops. A production bug surfaced by the test delta — a routine
tester fail loop: the test reviewer does not return the row to In Progress.

## Project documentation (Projects in uwuwu) — the mandatory contour

Project docs are the source of truth, not furniture. Sections: README (a machine-readable annotation + Value/Non-goals/Success criterion) · Design Spec (a single design doc: User Story / Use Case / Stack / NFT / C4 architecture L0–L2 with «Как тестируем» / Domains-Aggregates opt.) · Runbooks · Deployment (environments, access) · ADR · `Модель (LikeC4)` when present.

**Reading — before any project task (hub: docs/Projects/<proj>/…):**
- minimum: README (boundaries/goals) → Design Spec (requirements/stack/architecture) → ADRs on the task's topic; Deployment — when it touches infra, credentials.
- how: `uwuwu_docs_read(slug: "<project>/<doc>")`.
- in the task/PR body reference the docs and ADRs you relied on.

**Updating — in the same session as the change (the doc must not lie):**
- architecture/topology changed → Architecture in the Design Spec; if `Модель (LikeC4)` exists → edit the DSL there, validation — `likec4 validate` (the interactive view is dead — see the `visual-diagrams` skill; PNG export is alive)
- a new/changed requirement → a record in the Design Spec per the appearance rule: a requirement (US/UC/NFT) enters the spec only through an owner record (a task/dialog/commit with a date, a quote); «a requirement out of thin air» is invalid — an agent does not invent, behavior without a record → flag the owner; a transfer from a derived doc — the source «transferred from: <doc>» + a «not confirmed» mark (until confirmed the record does not justify new behavior); IDs are not reused, withdrawn records remain
- you justify code/test behavior with a requirement → reference the record ID in the spec (traceability); the reviewer verifies the record against the spec
- a project's stack — the allow-list of the spec's «Стек» section; a new library/framework outside the frame — only agreement with the owner
- audit check (dreamer/audit): code behavior without a spec record → flag the owner; a withdrawn/suspended requirement with live behavior → a task for removal
- the old project form (Domains/Stack as separate docs) — do NOT migrate it on your own: migration to the Design Spec is a separate task/owner order; deleting old docs is allowed only together with creating the project spec
- a new environment/service/credential/secret → Deployment (secret values — placeholders, the keys stay with the owner)
- a reproducible procedure → a Runbook (the project's subfolder)
- an accepted architectural decision → an ADR is maintained by the dreamer post-factum (do not create it yourself; the format — agents/dreamer.md, step 4)
- the ADR obsolescence chain → a new decision retires its replaced predecessors: the old ADR gets the status «Superseded by ADR-NNN · `<date>`» — the dreamer's duty when creating a new ADR (mechanics — agents/dreamer.md, step 4)
- found stale content/an error in the docs → fix it right away or open a task (`uwuwu_task_create(project: "uwuwu")` — it lands in Analys, an analyst will handle it); do not walk past.
- you quote a fact from the wiki/persona in a task, PR, or doc → open the source in the same session (wiki/ADR — `uwuwu_docs_read`, a PR — `gh pr view`, code — by reading); a number is not evidence; a record contradicts the source → fix the record (the persona — only flag the owner, they maintain it); the class — an attribution into the existing experience article after a live read (dedup — agents/dreamer.md, step 5; the dreamer accumulates experience), not a new doc.
- rich docs with HTML blocks — do NOT overwrite mindlessly — HTML blocks are portable, but a full body replace recreates the doc.

Visuals — two layers (the `visual-diagrams` skill): one-off diagrams in tasks/experience (static SVG/mermaid/vesper) vs the project's living model (LikeC4).

The factory is only an alarm clock: it wakes on new comments/body edits; a task's Done cleans up the task env. Legacy worktrees of merged PRs (wt/, .worktrees/ under the master checkout) — the factory removes them itself — a start pass and hourly; guards: clean, the branch is an ancestor of origin/master, no open PR, not an active task, a 24h grace after merge; a gh failure stops the pass without decisions.

### Channels: body vs comments

**The body** — a clean document: the statement, the plan/solution, verification, the final report, diagrams, artifacts. Everything that survives the task — into the body.

**Comments** — a live dialog with the user (their superpowers: threads/replies, resolution, attachments):
- a question to the user → a comment; the user answers **in a thread (reply)** — the answer wakes the agent
- **a question went out — verify the landing**: after a question comment (`uwuwu_task_comment`) before setting
  Needs attention make sure the call did not fail and the comment landed (`uwuwu_task_get` — the comment tail);
  a failure in a long turn is invisible, a non-landed question loses the owner until the
  next wakeup (the 05.11 incident). The channel — the `project` parameter (default uwuwu; examples — in spawn prompts)
- **replying to the user in a thread — `uwuwu_task_comment` with `reply_to`** (a quote anchor of the
  counterpart's line). A new topic (a report, a PR) — a comment without an anchor; the feed — `uwuwu_task_get` (the comment tail)
- a PR link when ready for merge (renders natively) — the only status comment
- **noise is FORBIDDEN**: «taken», intermediate reports, body duplicates. Turn progress — the kanban status
  (In Progress → Review), results — into the body. A comment without a question to the user = noise
- user attachments in a comment — for discussion; working screenshots the user puts into the body/comments (visible as links in the text, github-user-assets — download via the link) — reference them
- **agent attachments — `blob_put`** (#1292): a file (a screenshot etc.) → key + presigned URL (TTL 7 days) → the link into the body/comment/doc with text tools; the link expired → `blob_get(key)` re-sign and replace in the carrier by hand (re-signing does not edit the carrier itself)
- the user **resolves** threads for tidiness — this is NOT a signal to the agent, do not wait and do not react
- the factory comments **only exceptions** (a session lost / failed to start ×3); restarts and mechanics — in the server log, not in the task
